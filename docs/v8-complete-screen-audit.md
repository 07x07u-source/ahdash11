# AHDASH 11 - V8 Complete Screen Audit

Status: evidence pass before implementation  
Source of truth: `output/pdf/ahdash11-all-screens-v7.pdf` (73 pages, 45 rendered screens/states)  
Reference renders: 1280x720 and 844x390, Light and Dark  
Method: every rendered screen was opened visually. Percentages below are measured visual estimates of the usable application canvas, not claims of mathematical precision.

## Audit key

- **Width / height usage**: approximate primary-content bounds as a share of the usable canvas.
- **Dead space**: unexplained space after excluding safe area and deliberate breathing room.
- **Scale**: `text / icon / image / control`, judged against V8 targets (body 14-16, primary title 24-36, glyph 18-24, hit target 44-48, primary control 48-52).
- **Decision**: one of KEEP, POLISH, RECOMPOSE, REBUILD, MERGE, MOVE, HIDE, REMOVE.
- When a row contains two decisions, the first is the visual action and the second is the information-architecture action.

## Auth state coverage findings

- **Sign in**: implemented and rendered.
- **Create account**: implemented as a toggle using only username, email and password; no dedicated golden exists.
- **Guest**: implemented through anonymous/development authentication and must remain visible.
- **Google**: implemented through native Google Sign-In and Supabase ID-token exchange; displayed only when `GOOGLE_AUTH_ENABLED` and on native mobile.
- **Apple**: implemented as Supabase OAuth redirect and displayed only when `APPLE_AUTH_ENABLED` on iOS.
- **Forgot password**: no repository/controller/UI implementation found. Do not design or expose it in V8 yet.
- **Email verification/sent**: no explicit application state exists. Local Supabase config has confirmations disabled; remote configuration is not proven by this audit.
- **Loading and social loading**: supported by `AsyncLoading` and per-provider in-progress state.
- **Validation/server/offline error**: inline error region exists; compact mode currently ellipsizes it to one line and needs a non-clipping V8 policy.

## Cross-screen measured findings

1. Primary wide screens with unexplained dead space above ~25%: Team Setup, Helpers, Ready, Reveal, Result, Tournament Hub, Tournament Teams, Draw, Bracket, Tournament Match, Champion, Notifications, Settings, Premium, all onboarding steps, Friends, Blocked Players and Saved Games.
2. Screens that use area well but with the wrong composition: Home, Category Selection, Board, Match Setup, Solo Setup, Online Lobby, Team Detail, Game Selection, Classic Categories, Solo Result, Social Hub and Football Preferences.
3. Strongest V7 functional screens: Party Question, Online Match, Team Challenge and Solo Match Question. These need measurement polish rather than arbitrary rebuilding.
4. Repeated generic category art is visible in Party Category Selection, Board and Classic Categories. V8 must not create replacement art without rights and admin/data evidence.
5. The V7 frame currently uses horizontal gutters 16 / 28 / 48. This does not match the requested V8 rhythm of 20-24 / 24-32 / 32-40 and will be corrected at the token/layout layer after checkpoint specs are approved.
6. Several legacy screens use controls that visually read below the 44-48 target even if their Flutter hit test may be larger. V8 should make the effective target and visible affordance agree.

## Exact legacy/remnant audit

- Public `/wallet` exists only as a redirect to `/store`; the rendered public screen is Premium.
- Unrouted `features/store/presentation/wallet_screen.dart` and `store_screen.dart` still contain wallet/coin UI and are backed by wallet/store domain code. UI removal must not drop backend compatibility.
- User-facing coin strings remain in `currency_widgets.dart` and the unrouted store/wallet screens. Player profile and online rewards also contain real `coins` data.
- `report_problem_screen.dart` maps the internal source key `wallet` to user-facing `بريميوم والمشتريات`, which is acceptable public copy but should be renamed internally only if a safe compatibility plan exists.
- `BrandScaffold` contains a `DEV` badge guarded by `kDebugMode`, development environment and absent Supabase; it is not rendered in production configuration.
- `/play`, `/play/setup/:gameType`, `/categories`, `/solo`, `/solo/match`, `/solo/result` and `/online` remain public legacy/additional-mode routes. They are functional and must be moved or hidden deliberately, not deleted blindly.
- Four onboarding states repeat the same four concepts found in How to Play. Product ownership must choose the first-launch teaching policy before removal.
